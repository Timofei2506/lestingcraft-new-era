# Supabase: экономика, маркетплейс, друзья, скины

Проект: **LestingCraft** (`dcrtynmqrywsrgqxmmid`, eu-west-1, Postgres 17).

Игровой сервер (Cloudflare Worker + Durable Objects) остаётся источником истины по
мирам и сессиям. Supabase хранит то, что должно переживать комнату и быть общим
для игры, сайта и будущего мобильного клиента: кошелёк, покупки, скины,
маркетплейс и друзей.

## Что применено

| Таблица | Назначение |
| --- | --- |
| `profiles` | одна строка на игрока: `player_key` (32 hex, игровая личность) ↔ `auth_user_id` (вход на сайте) |
| `wallets` | баланс, `CHECK (balance >= 0)` |
| `wallet_ledger` | аудит каждого движения монет, `UNIQUE (profile_id, reference)` для идемпотентности |
| `currency_packs` | паки монет за реальные деньги, цена только на сервере |
| `topups` | платежи, `UNIQUE (provider, provider_ref)` — вебхук нельзя провести дважды |
| `store_items` | скины, плащи, эмоции |
| `entitlements` | что игрок уже купил |
| `market_listings` / `market_orders` | игрок-игроку, лот эскроует предмет |
| `friend_requests` / `friendships` / `player_blocks` | друзья и блокировки |
| `player_link_codes` | одноразовый код, которым аккаунт сайта привязывается к игровой личности |

Функции: `my_profile`, `store_buy`, `equip_skin`, `market_list`, `market_cancel`,
`market_buy`, `friend_request`, `friend_accept`, `friend_decline`, `friend_remove`,
`friend_list`, `svc_topup_credit` (только service role).

## Модель безопасности

- RLS включён на всех таблицах, **политик на запись нет вообще**: писать можно
  только через `SECURITY DEFINER`-функции, которые проверяют вызывающего.
- Кошелёк нельзя пополнить из клиента: `svc_topup_credit` отказывает всему, что
  не имеет роли `service_role`. Вызов идёт из платёжного вебхука.
- **Стартовых монет нет.** Новый кошелёк — ровно `0`. Единственные источники
  монет: оплаченный пакет и продажа на маркетплейсе.
- Повторный вебхук не начисляет второй раз (уникальный `provider_ref` + ledger).
- `friend_request` не отличим для существующего и несуществующего ключа: эндпоинт
  нельзя использовать для перебора `player_key`.
- Маркетплейс берёт 5% (`fee_bps = 500`) с продавца, покупатель платит ровно цену лота.
- Блокировка игрока запрещает и покупку его лота, и заявку в друзья.
- `player_key` **не** попадает в публичные выборки: `friend_list()` отдаёт его
  только владельцу строки, для остальных он не нужен.

## Как применять

```bash
cd Supabase
SUPABASE_ACCESS_TOKEN=sbp_... SUPABASE_PROJECT_REF=dcrtynmqrywsrgqxmmid npm run db:all
```

`db:apply` создаёт/обновляет схему (файл идемпотентен), `db:verify` прогоняет
сквозной сценарий (топ-ап → покупка скина → лот → продажа → друзья → проверка RLS)
внутри транзакции с `ROLLBACK`: боевые данные не меняются.

Токен и `service_role` живут только в секретах CI/Cloudflare, не в репозитории.

## Что ещё не подключено (осознанно)

1. **Платёжный провайдер.** Паки заведены, но `active = false`: включать, когда
   появится Stripe/Cloudflare-платежи и вебхук, который зовёт `svc_topup_credit`.
   До этого монеты в игре получить нельзя — и это честнее, чем «работающий» магазин,
   который не может списать деньги.
2. **Supabase Auth на сайте.** Схема готова (`profiles.auth_user_id`), но сайт пока
   без входа. Нужен экран входа и привязка `player_key` одноразовым кодом.
3. **Worker → Supabase.** Игровой сервер пока не знает про Supabase. Следующий шаг:
   `worker.js` вызывает `friend_list`/`store_buy` с `service_role`-ключом из секрета.
